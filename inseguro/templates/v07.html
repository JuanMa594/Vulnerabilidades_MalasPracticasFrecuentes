V07 · Cambiar precio except demasiado amplio

Cambia el precio de un producto por su SKU. Si algo falla, el backend se lo traga con except: pass y siempre dice "guardado". Prueba con un precio válido (30000) y luego con uno inválido (abc): mira la tabla y verás que en el segundo caso el precio no cambió, aunque el mensaje diga que sí.

Qué está mal

Un except sin tipo se traga cualquier error y no hace nada.

{% raw %}
try:
    precio = float(nuevo)
    cur.execute("UPDATE productos SET precio = %s WHERE sku = %s", (precio, sku))
except:          # atrapa TODO
    pass         # y lo ignora
mensaje = "Precio actualizado."   # se muestra pase lo que pase
{% endraw %}

Qué pasa por debajo

Si float("abc") falla (o falla el UPDATE), la excepción se descarta y el programa sigue como si nada. El mensaje "Precio actualizado" se muestra igual, así que la interfaz miente: dice que guardó cuando no guardó.

Cómo verlo pgAdmin

  1. En pgAdmin, mira el precio actual: {% raw %}
    SELECT sku, precio FROM productos WHERE sku = 'FE-001';
    {% endraw %}
  2. En la demo, cambia FE-001 a abc y Guarda: dice "Precio actualizado".
  3. Vuelve a correr el SELECT: el precio no cambió. Con 30000 sí cambia. La base delata la mentira.

Qué tan grave es Media

Fallos silenciosos: datos que "no se guardan" sin aviso, bugs imposibles de depurar, y encima oculta errores de seguridad (por ejemplo, un fallo al validar permisos que nadie ve).

Cómo se arregla

Capturar la excepción específica y actuar: mostrar o registrar el error y no afirmar que se guardó. {% raw %}
try:
    precio = float(nuevo)
except ValueError:
    mensaje = "El precio debe ser un número."
{% endraw %}
